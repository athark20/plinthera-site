Every agent. Explicitly permitted.

The checkpoint between your AI agents and the systems they act on. Before an agent issues a refund, grants access or exports data, your rules decide: go ahead, wait for a named person, or stop. Every decision is signed and kept.

How a request is handled

From the moment an agent decides to act to the moment the action reaches your systems.

  1. 1

    The agent asks first

    Right before it acts, the agent sends AgentPermit the action and its details, such as Refund.Issue for AED 4,200. Who is asking comes from the agent's sign-in, never from what the request says, and an agent that isn't registered can't act at all.

  2. 2

    Your rules decide

    Every action in the catalogue has a risk level, and your rules set the answer. For example, refunds up to AED 1,000 go through, larger ones wait for the finance lead, and bulk exports of customer data are refused. Rules are published as signed versions, so a new limit applies without a redeploy.

  3. 3

    A named person signs off

    When a rule says ask, the request waits with its details frozen. The accountable person approves or rejects it in the AgentPermit console or in a Teams card. If anything in the request changes while it waits, it is refused.

  4. 4

    There is no way around it

    Your systems accept agent actions from AgentPermit and nothing else, and a paired data-loss policy in Power Platform stops agents connecting to them directly. An agent that keeps testing a refusal is quarantined automatically.

  5. 5

    Every decision leaves a receipt

    Each decision is written to a receipt, signed with a key that never leaves your Azure Key Vault and chained to the receipt before it. An auditor can check any receipt independently, and altering one breaks the chain.

Nine checks, in a fixed order

Every request goes through the same pipeline, whether it comes from Copilot Studio, your own code or an MCP client. Any check can stop it.

  1. IdentityThe agent is identified from its sign-in token. A request that names a different agent is refused.
  2. Replay protectionEach request carries a key only that agent can use, so a retry never runs an action twice.
  3. Safety switchesA kill switch, per-agent quarantine and rate limits apply before any rule is read.
  4. Action checkThe action must be in the catalogue, and its details must be valid.
  5. Your rulesThe signed policy answers allow, ask a person, or deny.
  6. EnforcementIn a staged rollout, low-risk blocks can be logged before they are applied. High and critical actions are enforced from day one.
  7. Sign-offIf a person must approve, the request is frozen until they decide.
  8. ExecutionAgentPermit performs the action itself. Agents never hold the credentials for your systems.
  9. ReceiptSigned in Key Vault and chained to the receipt before it.

What every receipt proves

A log says what happened. A receipt proves it: who asked, exactly what was approved, what ran, and that nothing has changed since.

  1. 1Who asked, and for whatThe agent's identity as its sign-in proved it, the action, and its details.
  2. 2Exactly what was approvedA fingerprint of the request, taken when it was frozen for sign-off. The action that ran must match it.
  3. 3The chainThe fingerprint of the receipt before this one. Remove or edit any receipt and every later one stops matching.
  4. 4The signatureMade with a key held in your Azure Key Vault, which never leaves it. Anyone with the public key can verify the receipt without asking us.

Questions buyers ask

One step is added. Right before the real action, the agent asks AgentPermit and carries on only if the answer is allow. In Copilot Studio that is one connector action in the topic; in code it is one API call.

The agent stops at the checkpoint, because nothing runs without an allow. In production the gateway keeps at least one instance running at all times and is spread across availability zones.
